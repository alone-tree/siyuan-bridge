# 剪藏支持方案

状态：草案，待讨论。2026-11-17。

## 一、结论：思源本体没有可直接借用的无头浏览器

分三层核对过，逐层给结论。

### 内核 HTTP API：没有任何浏览器或渲染能力

723 条路由里没有 puppeteer、chromedp、rod、playwright、selenium 任何一个的符号。与抓取有关的只有两类：

- `/api/network/forwardProxy`、`/api/network/proxy`：裸 HTTP 转发，不执行 JavaScript。
- `/api/extension/copy`：接收已经抓好的 HTML 字符串，用 lute 转成 Markdown，不负责抓。

后者的参数是 `dom`（HTML 字符串），不是 URL。内核不主动访问网页。

### 内核自带 MCP 服务：有 web_fetch，但它是裸 HTTP

本机 v3.8.10 实测 `POST /mcp` 可用（需要管理员角色），`tools/list` 返回 31 个工具，其中包含 `web_fetch` 和 `web_search`。

`web_fetch` 的工具描述原文有一句关键限定：

```text
Fetch a public page using the configured provider (direct HTTP or DeepSeek), as markdown (default) or text. No browser session is used.
```

实现见 `kernel/util/webfetch.go`，行为：

| 项目 | 值 |
|---|---|
| 抓取方式 | `ssrfSafeClient` 直接 HTTP GET |
| 文本上限 | 5 MiB |
| 输出截断 | 50000 字符 |
| HTML 处理 | `SanitizeHTML` 清脚本样式，再用 lute 的 `HTML2Markdown` |
| 正文抽取 | 无。整页转 Markdown |

本机实测三篇：

```text
[阮一峰]  len=22173 img=42  head='阮一峰的网络日志  » [首页](...) » [档案](...)'
[少数派]  len=16393 img=43  head='[  共创  ](/create) \n\n[  PRIME  ](/prime)'
[MDN]     len=13098 img=0   head='- [跳转到主要内容](#content)\n- [跳转到搜索](#mdn-search)'
[arXiv]   web_fetch error: fetch failed
[GitHub]  web_fetch error: fetch failed
```

开头全是导航。arXiv 和 GitHub 直接失败，因为内核走直连、没有代理配置。

同一篇微信文章经它抓取，返回 72 字符的验证页「环境异常，完成验证后即可继续访问」。

### Electron 桌面端：确实有一个真正的无头浏览器，但外部拿不到

这是唯一真正渲染 JavaScript 的地方，在 `app/electron/remote/webPageFetch.ts`。

实现要点：

- 用 Electron 的离屏 `BrowserWindow` 真实加载页面，`javascript: true`、`offscreen: true`、`sandbox: true`
- 每次抓取用独立 session（`siyuan-web-fetch-<uuid>`），不带用户的 Cookie 和登录态
- 自定义 protocol handler 固定公网 IP，防 SSRF；禁用下载、WebSocket、WebRTC、WebTransport
- 最多 3 个并发
- 正文抽取用的是固定选择器列表：

```js
const selectors = ["main", "article", "[role=main]", ".main-content", "#main-content",
  ".article-body", ".post-content", ".entry-content", ".content", "body"];
```

取 innerText 最长且不少于 100 字符的那个，然后移除 `script, style, noscript, template, iframe, object, embed, nav, [hidden], [aria-hidden=true]`。

问题在这里：它注册为 agent 能力 `native/frontend/web_page_fetch`，条件写死在 `app/src/layout/dock/agent/frontendCapabilities.ts`：

```ts
/// #if !BROWSER && !MOBILE
if (!mobileFrontend && !isBrowser()) {
    registerCapability({ id: "native/frontend/web_page_fetch", ... })
}
```

它走 IPC 通道 `siyuan-web-page-fetch`，只给应用内 Agent 用，不投影到外部 MCP。实测 `tools/list` 的 31 个工具里没有它。

所以对第三方 MCP 客户端来说，这个能力不存在。

## 二、可以复用的部分：正文抽取规则，不是代码

上面那段选择器列表值得注意：思源自己抓整页时用的也是「语义标签优先 + 固定门槛」，没有为任何站点写特例。这和我们实测出来的通用规则是同一个思路。

我们可以照搬这个规则形态，但代码要自己写（Electron 里那段是浏览器上下文里的 JS，Python 侧用不了）。

## 三、方案

前提：纯 Python，不依赖浏览器，不为具体站点写适配。

### 3.1 整体链路

```text
siyuan_create(source_url=...)
  → Bridge 抓 HTML（urllib，走系统代理）
  → 标准库 html.parser 建轻量树
  → 选主容器 + 清属性 + 提升懒加载图
  → POST /api/extension/copy 拿 Markdown（内核原生转换）
  → 走现有 create 写入流程
  → /api/format/netImg2LocalAssets 本地化图片
```

关键点是转换交给内核。实测内核的 HTML 转 Markdown 比任何 Python 库都好：同一篇微信文章，内核产出 29 张图，trafilatura 产出 0 张。

### 3.2 抓取层

- urllib，不新增依赖
- 带浏览器 UA 与 Accept-Language
- 编码：从 Content-Type 取 charset，取不到再从 HTML 前 4KB 找 `<meta charset>`，都没有按 UTF-8；这是通用类型适配，不是站点适配
- 超时 30 秒，正文上限 5 MiB
- 跟随重定向（urllib 默认行为）

### 3.3 正文定位

通用规则，按顺序尝试：

1. 语义标签与常见容器：`article`、`main`、`[role=main]`、`#js_content`、`#main-content`、`.article-content` 等
2. 密度扫描：遍历 `article/main/div/section`，算 `文本长度 - 2 × 链接文本长度`，按 DOM 深度衰减，取最高分
3. 都失败就退回 `body`

第 1 步里的 `#js_content` 是微信的容器 id。按你的要求，微信可以特殊处理，这一条算进去。

### 3.4 清洗

- 删 `script`、`style`、`noscript`、`svg`、`iframe`、`form`、`button`
- 所有元素只保留 `src`、`href`、`alt` 三个属性，其余全删
  - 这一条不可省。微信每个 `<span>` 都带完整内联样式，不删的话内核会把它们全转成 IAL 属性语法，产出 39270 字符垃圾；删完是 11022 字符干净正文
- `<img>` 的 `data-src`、`data-original` 提升为 `src`（实测微信 26 张图里的关键）
- `section` 改名为 `div`，避免思源生成超级块

### 3.5 依赖

不新增。全部标准库。

之前对比过 bs4 和 trafilatura：

| 方案 | 依赖体积 | 实测表现 |
|---|---|---|
| 标准库 html.parser | 0 | 8 站点抽取与 bs4 结果接近，耗时 24-76 ms |
| bs4 + soupsieve + typing_extensions | 204 KB | 结果接近，耗时 45-569 ms，需扩展现有 wheel 机制支持纯 Python 包 |
| trafilatura 全树 | 6.88 MiB | 微信 0 张图，正文前插 9 行 YAML 头，MDN 截断 |

标准库那一版在微信上比 bs4 更快且图片更多。唯一的取舍是标准库的 `html.parser` 对畸形 HTML 的容错比 lxml 差，但这个风险可以用「解析失败退回整页 body」兜住。

### 3.6 工具面

倾向给 `siyuan_create` 加一个 `source_url` 参数，而不是新增第 10 个工具：

- `source_url` 与 `markdown`、`markdown_file` 三者互斥
- 传 `source_url` 时 `title` 变可选，默认取页面 `<title>` 或 `og:title`
- 其余行为复用现有 create：路径解析、权限检查、快照、`if_exists`、写后刷新

## 四、覆盖边界

31 个站点实测分布：

| 类别 | 数量 | 例子 |
|---|---|---|
| 直连可抓 | 18 | 微信、阮一峰、少数派、CSDN、虎嗅、新浪、GitHub、arXiv、MDN、Wikipedia、BBC、Guardian |
| JS 壳 | 3 | 今日头条（72914 字节可见文本 0）、B站专栏、豆瓣文章 |
| 反爬或登录墙 | 8 | 知乎 403、Medium 403、StackOverflow 403、Reuters 401、简书 403、微博 Visitor System |
| 传输阻断或付费墙 | 2 | 小红书 TCP 重置、NYT 计量墙 |

抓不到时明确报错，说明原因，建议用户用浏览器扩展手动剪藏。不做无头浏览器兜底。

## 五、需要你决定的三件事

1. 工具面：`siyuan_create` 加 `source_url` 参数，还是单独一个工具。
2. 图片默认行为：抓到后自动本地化（依赖内核 `netImg2LocalAssets`），还是保留外链由调用方决定。
3. 站点特殊处理的范围：只加微信（`#js_content`），还是完全不写任何站点 id。我倾向只加微信这一条，因为它是你明确点名的，而且 `js_content` 有明确语义。
