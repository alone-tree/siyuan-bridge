## 2 结论

列表块 read 展开、列表项单选改文字、整棵替换、插入定位、分页与预算控制这些主路径可以正常工作。

存在两类必须修的问题。一类是范围与引用保护不完整，会在用户没有选择的范围内删掉内容、打断外部引用，属于数据安全问题；另一类是提交内容解析丢层级、任务项旧文字残留、块属性被清空，属于内容正确性问题。

按当前代码，AI 只要按 schema 正常调用就可能触发前一类问题，不需要任何异常参数。

## 4 逐条说明

### D1 跨父范围不校验

代码位置 `source_code/mcp_server.py:4831`、`4849`。范围校验 `_validate_list_range` 只在 `target_blocks[0].type` 为 `l` 或 `i` 的分支里调用。起点是普通段落时整段校验跳过，执行段仍按原范围删除。

真实调用（delete）：文档为 `[1]Intro`、`[2]list`、`[3]A`、`[4]B`、`[5]C`、`[6]Tail`，选 `start_index=1`、`end_index=3`，返回成功，删除 `[1]`、`[2]`、`[3]`。思源删列表块时连带 `B`、`C`，最终文档只剩 `Tail`。

真实调用（default_block_replace）：文档为 `[1]前置段落`、`[2]list`、`[3]A`、`[4]B`、`[5]尾部段落`，选 `1` 到 `3`，提交 `- X`，返回成功，`B` 同样消失。

预期按方案 5.5 与 5.7，跨父容器范围应报 `validation:operation_order`，且不得创建快照。

### D2 被引用段落被静默删除

代码位置 `source_code/mcp_server.py:4950`，反链保护只在 `action` 为 `delete` 或 `default_block_replace` 时执行。列表项单选分支在 `4698` 到 `4704` 直接 `client.delete_block` 删除后续段落，没有进入保护。

真实调用：列表项含 `Parent` 与 `Extra protected paragraph` 两段，先用另一篇文档建立指向该段落的 `siyuan://` 引用，`siyuan_operate(action=check_backward_references)` 确认 1 条关系。随后对列表项执行 single 替换提交 `- Parent changed`，返回成功，被引用段落消失，`reference_policy` 未参与。

预期按 DEVELOPMENT_GUIDE「修改写入模型时必须验证」，任何会消失的块 ID 都要在快照前检查引用，存在外部关系时拒绝。

### D3 提交层级被压平

代码位置 `source_code/mcp_server.py:1035` 到 `1040`。`parse_submitted_list_items` 对所有子行 `strip()`，缩进信息不进入解析结果；非列表的续行统一进 `follow_lines`，执行时插到首段落之后。

真实调用：向含 `Existing child` 的列表项提交 `- Parent changed\n  - New child\n    - New grandchild`，结果 `New child` 与 `New grandchild` 成为同级，`Existing child` 排在两者之后。

真实调用（续行）：提交 `- Parent changed\n  - New child\n    child continuation`，结果是 `child continuation` 出现在 `Parent changed` 下的正文位置，而不是挂在 `New child` 下。

预期按方案 5.4 与第 6 节，嵌套深度与续行归属都要保留。

### D4 任务项旧续行残留

代码位置 `source_code/mcp_server.py:4686` 到 `4692`。任务项分支保留 `source_markdown` 首行之后的全部内容，清理原段落只在非任务分支执行。

真实调用：原任务项为 `- [ ] Task` 加续行 `old continuation` 加子项 `Child`，提交 `- [x] New task\n  new continuation`，结果读回为 `[X] New task` / `new continuation` / `old continuation`，三行并存，`Child` 保留。

预期按方案 5.3，原全部文字段落应被本次提交替换，只保留子列表。

### D5 块属性未保留

代码位置 `source_code/mcp_server.py:4692`、`4700` 直接调用 `client.update_block`，没有经过 `4541` 的 `_update_block_preserving_attrs`。

真实调用：用 sisyphus MCP 给列表项设 `style` 与 `custom-test-mark`、给首段落设 `custom-p-mark`，再执行 single 替换，然后用 SQL 读 `ial`。列表项两个属性都在，首段落只剩 `id` 与 `updated`，`custom-p-mark` 消失。

预期按 DEVELOPMENT_GUIDE「single_block_replace 和 table_edit 必须保留块属性」。

### D6 同起终点被误判

代码位置 `source_code/mcp_server.py:4860`，只按 `len(target_blocks) == 1` 判断是否走 5.2 细则，不检查是否传入终点。方案 5.1 第 4 条要求同时传 `end_index` 与 `end_id` 时走 5.5 整棵替换，方案第 366 行的合法示例也包含单点范围。

内存复现：选列表项并传相同起终点，实际只更新首段落，引用检查与子树扩展都没有执行。真实环境未触发该分支。

### D7 项内空行分段被拒

代码位置 `source_code/mcp_server.py:4911`。列表判定后仍调用 `markdown_has_multiple_blocks`，该函数只看空行。方案 5.1 第 197 行已经提醒列表判定要早于旧多块检查。

内存复现：提交 `- parent\n\n  second paragraph` 报 `validation:wrong_shape`；同样内容去掉空行可以成功。真实环境未触发该分支。

### D8 两端编号不一致

Python 侧 `build_display_blocks` 用 `"{{" not in block_md` 判断是否回退整树，插件侧 `hasEmbedMarker` 要求同时出现 `{{` 与 `}}`。列表 markdown 含 `{{` 但不含 `}}` 时，Python 不展开，插件展开。

真实调用：文档列表项文字含 `{{ 无闭合`，引用阅读只返回 1 个展示块（整段列表原文）。同一份 markdown 用 `block-index.js` 计算得到列表块加列表项共 4 个序号。另外用 fixture 级对照复现同一分歧。

预期按 ARCHITECTURE.md，插件角标与 `include_block_ids=true` 的 `index/id/type` 必须一致。

### D9 插入摘要为空

真实调用：以带子项的列表项为锚点执行 `insert_after`，插入的位置正确（落在整棵子树之后、成为同级项），但返回体里「插入内容」显示 `（无）`，AI 无法从返回确认写了什么。
