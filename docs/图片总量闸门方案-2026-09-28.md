# 读文档图片总量闸门方案 — 定稿（2026-09-28）

## 背景：要解决什么

`read_inline_images` 开启后，`siyuan_read` 把窗口内全部图片 base64 后塞进单笔 MCP 响应，没有任何总量上限。2026-09-26 读《W5 营销》时，5 张截图原始共 10,679,543 字节，base64 后约 14.2 MB，超出 MCP SDK 客户端默认读缓冲 10 MB（10,485,760 字节），连接被客户端掐断，连续重试 4 次（不同 token_budget/block_limit 参数）全部同样失败——失败与参数无关，因为预算按每图 1,568 token 名义计价，与实际字节无关。

根因判定：主责在思源桥响应无总量闸门；能力库与 DSH 均按 SDK 默认行为工作，无缺陷。详细证据链见 2026-09-28 会话结论（不在本文重复）。

## 行业调研结论（方案依据）

查证了 Codex、Claude Code、ChatGPT 网页、DeepSeek、chrome-devtools-mcp 的图片处理链路，共同模式：

1. 全行业都在进模型前把图片缩到有效分辨率（Claude 1568/2576px、OpenAI 2048px、DeepSeek 约 1300×1300 总像素）——超出部分模型看不见，服务端反正会缩。
2. 没有一个产品允许单条大响应杀死会话：Codex/Claude Code 缩不动就换占位文本；chrome-devtools-mcp 截图 ≥2 MB 不内联、存临时文件给路径（"Reference over Value"）。
3. token 按像素计费、与文件字节无关，压缩不省 token；压缩省的是传输字节。
4. chrome-devtools-mcp（与思源桥同处境的 MCP server）的修法：server 不硬编码客户端限制，提供 opt-in 参数让部署者自选。

关键来源：Codex commit a6f435e（image_preparation.rs）、Claude vision 与 vision-coordinates 官方文档、OpenAI Images and vision 官方文档、DeepSeek 官方图像理解指南、chrome-devtools-mcp PR #1823。

## 定稿决策（2026-09-28）

不做图片压缩、缩放、转码（后续版本再评估，可选 Pillow 路线已调研过，暂缓）。本版只做**单笔总量闸门**：

### 1. 预算定义

- 新增读侧专用常量：单笔响应图片累计 base64 预算 = 9 × 1024 × 1024 字节（9,437,184）。
- 只称**图片部分**的字节体积；文本、大纲不受此预算约束（由现有 token_budget 机制管理，行为不变）。
- `ASSET_LARGE_FILE_THRESHOLD_BYTES`（20 MB）**保持不动**——写入侧 `insert_assets`（mcp_server.py :858、:3623）继续使用；read 侧不再引用它，读写两侧解耦。
- base64 后大小按 `(len(data) + 2) // 3 * 4` 计算，无需真实编码两次。

### 2. 装填语义：前缀装填，遇超即停

按文档顺序逐图累计：

- 装得下（累计 base64 字节 ≤ 预算）→ 内联；
- 碰到第一张装不下的图 → 该图声明，**它之后的所有图不再尝试、全部声明**（内联的一定是文档顺序前缀，行为可预测）；
- 极端情况第一张就超预算 → 一张不放，全部声明。

与现有 token_budget 独立并存：token 预算决定文本窗口大小，字节预算决定窗口内哪些图能内联。

### 3. 网络图：流式称重，不需要预知大小

- 现有 `fetch_url_bytes`（mcp_server.py :4925）已支持流式下载边下边计数、超线即中止（64 KB 块粒度）。
- 改动：下载中止线从固定 20 MB 换成**剩余预算**（9 MB − 已装填字节）。下载中止即视为该图超限 → 声明 → 停止装填。
- 下载失败（HTTPError/URLError/超时）走现有「读取失败」声明，不影响已装填的图。
- 可选优化（暂不做）：下载前看 HTTP `Content-Length` 预判，不可靠（chunked 无此头、可谎报），流式计数已够。

### 4. 超限声明（沿用并微调现有机制）

声明在图片原位置写入，不无声跳过。文案区分两类：

- 本地图：`[图片未返回：超出单笔 9 MB 安全范围。文件：<本地绝对路径>，可用平台读图能力直接查看]`（附件已由 `extract_attachments` 提取到 `ai_workspace/attachments/<doc_id>/assets/`，路径现成）
- 网络图：`[图片未返回：超出单笔 9 MB 安全范围。原地址：<URL>，可用平台的网页获取工具下载后查看]`

网络图无本地副本，URL 即最诚实的引用；URL 失效的图任何人都读不到（思源本体显示同样依赖该 URL 实时可拉）。

### 5. 响应头部提示行

超限发生时，`siyuan_read` **正常返回**（不整体 isError——整体报错会丢掉已读到的文本），头部追加一行，例如：

`图片共 N 张，已内联前 M 张（合计 X MB）；其余 K 张超出单笔 9 MB 安全范围未返回，请按各图位置的路径单独读取。`

- X（已装填合计）精确；K 张的合计大小：本地图可 stat 汇总，网络图不计入（未下载不知大小）。

### 6. include_large_images=true：逃生门

语义重定义：无视 9 MB 预算，窗口内全部图片强制内联。

- 用途：特殊客户端/场景明确支持大消息时使用。
- schema 描述必须如实写明风险：超过 10 MB 时在默认配置的客户端（DSH、能力库、Claude Desktop 等）会断连，属明知风险的自担选项。
- 保留参数名不变，仅重定义语义。

### 7. 明确不做的事

- 不做图片压缩、缩放、转码、格式转换（含 GIF 取帧）；
- 不做 Content-Length 预判；
- 不新增设置项（9 MB 固定，不暴露配置）——2026-10-10 修订：MCP 配置页新增「高级配置」，「单次读取时总图片体积上限」写入 `config.local.json` 的 `inline_image_budget_mb`（默认仍 9 MB，不限上下限），本条「不暴露配置」作废；
- token 计价（每图 1,568）不变；token_budget、block_limit 行为不变；
- 写入侧（insert_assets）20 MB 阈值及其行为不变。

## 被本方案修订的原决策（docs/图片内联需求-2026-09-14.md）

- 原决策 3「单张体积上限 20 MB + include_large_images 强制内联」→ 被「单笔 9 MB 总量闸门 + include_large_images 无视预算逃生门」取代（20 MB 单张上限在 10 MB 传输现实下是自杀设计：强制内联 8-20 MB 单图必断连）。
- 原需求第 3 条「不限制张数」、第 4 条「不允许因图片太大省略」→ 修订为「受单笔 9 MB 总量约束，超出按第 5 条原位声明并保留路径/URL」。这是明规则修订，非私自省略。
