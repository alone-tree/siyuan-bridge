# 系统笔记本登记表简化需求

- 日期：2026-10-10
- 状态：需求确认中，未排期实现
- 关联背景：插件弹窗「思源桥部分系统文档维护失败」误报；系统文档定位机制自 v1.5.1 起复杂度持续上升

## 1. 背景与动机

### 1.1 现状机制

插件每次激活（安装、更新、启动思源、重新启用插件）维护六类系统文档，并把每类文档的 ID、模板状态哈希写入插件数据区 `system_state.json`（schema v2，每类多个条目）。定位系统文档时：

- 插件端（`siyuan-plugin/index.js` 的 `findSystemDocs`）：登记 ID 优先，名称匹配兜底（当前名 + 历史名）。
- Python 端（`source_code/agent_notebook.py` 的 `load_agent_notebook`）：只认登记表 ID，登记失效即报「系统文档缺失」，无名称兜底。

维护流程共六个步骤，其中「系统文档登记表刷新」（激活末尾重扫笔记本、重写登记表）是纯登记表开销；其余各步骤内也穿插登记写入与逐步持久化。

### 1.2 登记表的历史由来

- v1.5.1（2026-08-01）：引入登记表 schema v2。动机：用户改过系统文档标题后按名称找不到，插件会静默创建重复文档；登记 ID 让「改名后的文档」仍被识别。
- v1.8.4（2026-09-21）：登记表迁入插件数据区（防集市更新删除插件程序目录导致登记丢失），并为托管指南增加模板哈希基线。

### 1.3 触发重新讨论的现象

用户环境频繁弹「思源桥部分系统文档维护失败」，但思源桥笔记本中六类文档齐全。2026-10-10 诊断结论：

- 该弹窗表示六个维护步骤中有步骤的思源 API 调用抛错，与文档是否存在无关；具体失败步骤尚未定位（需弹窗文案冒号后的项名或思源 DevTools console 警告）。
- 已排除：登记表缺项（六类齐全且当日刷新）、模板 manifest 哈希不一致（源码与安装目录全部 MATCH）。

### 1.4 决策动机（用户判断）

登记表的核心收益是「用户改名后仍能识别系统文档」。用户判断这不是真需求：用户没有动机修改系统文档标题，为防一个低概率行为引入登记表、逐步持久化、ID 失效清理、双端一致性等持续复杂度，得不偿失。登记表机制应取消，系统文档定位退回思源笔记文档名匹配。

## 2. 已定决策

1. 取消系统文档登记表机制，`system_state.json` 的 `documents` 注册表不再写入、不再读取。
2. 系统文档定位退回文档名匹配：当前名 + 历史名（`SYSTEM_DOC_NAMES` + `LEGACY_DOC_NAMES` / `LEGACY_NOTEBOOK_NAMES`），大小写不敏感。名称匹配能力在两端均已存在，本需求是删除登记依赖，不是新写匹配逻辑。
3. 接受行为变化：用户改过某系统文档标题后，插件按名称找不到，会以标准标题创建新文档；改名后的旧文档沦为普通文档（见 3.3）。
4. 隐私规则定位同样退回名称匹配，依赖 fail-closed 保证安全（见 3.4）。

## 3. 方案要点

### 3.1 插件端

- `findSystemDocs` 只按名称匹配；删除登记 ID 优先分支。
- 六个维护步骤中「系统文档登记表刷新」整体删除；各 `ensure*` 步骤删除登记记录与逐步 `persistState()` 调用，只保留文档本身的查找/创建/模板升级。
- 托管指南防误覆盖退回哈希现场判断（现有 `ensureManagedGuide` 无基线分支已实现该逻辑）：导出内容哈希命中当前模板或 `manifest.historical_normalized_sha256` → 可升级覆盖；不命中 → 视为用户修改，不覆盖。`user_modified` 不再持久化。
- 「关于思源桥」维持「正文不等于模板即覆盖」策略（现状对用户改动本就不保留，行为等效）。
- 「工作空间索引」占位符判断改现场哈希计算；`updated` 时间戳本来取自实时查询，不受影响。

### 3.2 Python 端

- `load_agent_notebook`：
  - 笔记本定位改为 `lsNotebooks` 按名称匹配（`match_notebook_name`，含历史名），替代 `active_workspace_key` 缓存定位；多个同名笔记本取第一个。
  - `_list_system_docs` 返回后按 `match_doc_key(hpath)` 分类，替代登记 ID 过滤。
- `source_code/system_state.py`（`load_system_state` / `active_system_ids` / `document_entries`）随登记表取消删除；`is_privacy_rules_document` 简化为纯名称匹配。
- 插件数据区保留：`config.local.json`、`telemetry.json`、`privacy_rules.json` 缓存、`block-index.json` 不受影响；`runtime_data.py` 中 `SYSTEM_STATE_FILE` 定义清理。

### 3.3 行为变化（明确接受）

- 用户改系统文档标题：该文档不再被识别，插件按标准标题新建；旧文档成为普通文档。
- 用户改「隐私规则」标题：找不到 Privacy Rules 文档，`siyuan_start` 失败关闭并提示重新启用插件重建——宁可拒绝服务，不在无隐私规则状态下放行。
- 用户删除 Privacy Rules 后新建同名空文档：解析出空规则集，与现状名称兜底分支行为一致；该文档对 AI 的硬隔离不变。

### 3.4 连带收益

- 维护步骤从六步减为五步（删除「登记表刷新」），插件激活的 API 调用量和弹窗失败面变小。
- `system_state.json` 整个文件退出维护清单，双端（JS/Python）状态一致性、ID 失效清理、逐步持久化等复杂度整体移除。
- 集市更新丢登记表一类问题（v1.8.4 迁移要解决的动机）不复存在。

## 5. 待决定项

1. 重复文档弹窗：同名多篇系统文档目前全登记并弹窗提示手动删除。取消登记表后是否保留该弹窗（仅提示，不自动处理）？
2. `system_state.json` 残留：升级后旧文件静默弃用（推荐，保留回滚兼容）还是导入时清理？
3. 版本：建议 MINOR（无工具契约变化，内部机制简化）。

## 6. 验收标准

- 未改名的存量用户升级后：激活插件不再写 `documents`；六类文档按名称全部识别，不新建重复文档。
- 改名场景（人工构造）：旧文档脱离系统文档身份，插件新建标准标题文档；Privacy Rules 改名时 `siyuan_start` 失败关闭且提示可操作。
- MCP 全部工具行为不回退：搜索、读取、写入的隐私过滤与系统文档硬隔离结果与改动前一致。
- 全量 `python -m pytest tests -q` 通过；导入脚本 `--fresh` 与普通导入在测试工作空间验证。
- 弹窗根因（维护步骤 API 报错）与本需求独立，不因本需求关闭；取消登记表仅消除其中「登记表刷新」一个失败源。
