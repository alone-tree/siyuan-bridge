# 收集箱支持方案（2026-11-17）

> 草案，未实现。核对基准：思源 v3.8.10（本机内核 3.8.10）、仓库 master、思源各版本 tag 源码。
> 定案实现后，工具契约并入 `ARCHITECTURE.md` 对应章节，本文删除。

## 1. 结论摘要

把收集箱做成一个虚拟笔记本，全部能力复用现有 9 个 MCP 工具，不新增工具：

- `siyuan_list` 能看到 `/收集箱` 及其条目，权限列恒为 `read_only`。
- `siyuan_read` 能读条目，只走普通阅读，不提供引用阅读。
- `siyuan_find` 能把收集箱内容纳入搜索。
- `siyuan_edit` 对收集箱条目直接拒绝。
- `siyuan_doc_manage(action="move")` 把条目移入普通笔记本，移动即从收集箱删除。

### 2.1b 闪记是另一个功能，不是收集箱的本地实现

思源官方用户指南（`app/guide` 术语表）原文：收集箱（Inbox）是临时存放待处理信息的容器，「在思源中，收集箱是云端快速记录功能，通过微信发送或 API 调用将文本暂存到云端，之后可在收集箱面板中将其移动到文档中进行整理。该功能需要订阅会员。」这是云端那套。

用户澄清：闪记和收集箱是两个东西。收集箱是云端功能，只有移动到普通笔记本后才进入本地文档体系；闪记是本地目录机制，独立于收集箱。下面记录闪记的事实，仅作区分参考，不纳入本方案：

| 证据 | 内容 |
|---|---|
| `kernel/util/working.go:250` | `ShortcutsPath // 用户家目录下的快捷方式目录路径 home/.config/siyuan/shortcuts/` |
| `kernel/model/shortcuts.go:29` | `shorthandsDir := filepath.Join(util.ShortcutsPath, "shorthands")` |
| `kernel/model/shortcuts.go:82` | 读 `Conf.FileTree.Load().ShorthandSavePath`（配置注释为「闪念速记存储路径」） |
| 自动消费 | `AutoConsumeShorthandsJob` 定时调 `MoveLocalShorthands`，把本地 shorthands 目录内容转成文档 |
| 路由 | `/api/filetree/moveLocalShorthands`；v3.0.0 无，v3.5.0 / v3.8.0 / v3.8.10 / master 有 |

本机实测（2026-11-17）：`C:\Users\Zinger\.config\siyuan\shortcuts` 不存在，全盘无 `shortcuts` 目录；`conf.fileTree.shorthandSavePath` 与 `shorthandSaveBox` 均为空串；前端构建包中 `moveLocalShorthands` 引用 0 次。本机只有云端那 2 条。

含义：两者的列表与移动接口完全不同，不能合并处理。本方案只处理收集箱（云端），闪记不在范围内。

### 2.5 原生移动的真实链路

v3.8.10 前端 `Inbox.move()`：`getShorthand` → `planDocCreate` → `createDocByParent` → `removeShorthands`。

官方内核 MCP `kernel/mcp/tools/inbox.go` 的 `convert`：能拿到结构化目标时用 `model.CreateDocByParent`，否则用 `model.CreateDocByMdSync`；只在成功条目上调用 `RemoveCloudShorthands`，失败条目保留。

v3.8.0 前端 `Inbox.ts` 的 `move()` 用 `/api/filetree/createDoc`（路径式）后 `remove(ids)`。

## 3. 已定决策

| 编号 | 决策 |
|---|---|
| D1 | 收集箱是特殊笔记本，不新增 MCP 工具，全部复用现有工具面 |
| D2 | 收集箱条目只读：可 list、read、find，不可 edit |
| D3 | 移动默认语义即从收集箱删除，与思源原生一致 |
| D4 | 移动复用 `siyuan_doc_manage(action="move")`，不维护第二套动作 |
| D5 | 条目定位优先标题，标题重名时用 oId 消歧；虚拟笔记本是单层的，路径只拆一次，标题里的 `/` 原样保留不影响定位，仅在移出写文档标题时转全角 |
| D6 | 不做批量移动 |
| D7 | 不做「插入到当前文档」 |
| D8 | 收集箱条目只用普通 read，不提供引用阅读 |
| D9 | 收集箱内所有条目的权限都为只读`read_only` 。不经过隐私规则管理（本来就是网络公开资料）|
| D10 | 收集箱内容进入 `siyuan_find` 搜索范围 |
| D11 | `siyuan_edit` 对收集箱条目报错，文案固定为「这是收集箱文档，只读。需要编辑请先用 `siyuan_doc_manage` 移出收集箱」 |

| D14 | 复用思源原生动作和接口，不自造转换规则 |

| D16 | 不依赖订阅状态做功能开关；以用户本地实际能看到的为准，收集箱为空时不展示该笔记本 |

## 4. 实现设计

### 4.1 虚拟笔记本定位

虚拟名由桥在每次调用时按 `knowledge_base/notebooks.json` 缓存与真实笔记本名比对算出：

| 情况 | 虚拟名 |
|---|---|
| 无同名真实笔记本 | `收集箱` |
| 已有真实笔记本叫「收集箱」 | `收集箱(系统)` |
| 真实笔记本同时占用「收集箱」「收集箱(系统)」 | `收集箱(系统)(2)` |
| 依次递增 | `收集箱(系统)(n)` |

比对用缓存，不额外请求内核。缓存过期可能算错一次，下次 `refresh` 后自愈。

展示条件（任一成立就不展示该虚拟笔记本）：

- 未登录或 token 失效（内核返回 `code != 0` 加 Language(31)）
- 无订阅或权限不足（`code != 0`）
- 网络不可达或请求异常
- 收集箱确实为空（`code == 0` 且 `paginationRecordCount == 0`）

以上原因都只在桥内部判断，不把云端错误抛给调用方。

索引：收集箱不写入 `knowledge_base/notebooks.json`，不写入 `docs.jsonl`，不参与索引。

路径解析顺序：先按真实笔记本与文档匹配；没有真实匹配且路径落在当前算出的虚拟名下时，才走收集箱分支。虚拟名本身已避开重名，因此不会与真实笔记本冲突。

### 4.1b 标题含 `/` 的处理

关键前提：虚拟笔记本是单层的。`/收集箱/<条目名>` 只有两级，第二级之后不再有层级，所以标题里的 `/` 不会被误当成下一级目录。这与其他工具的路径解析不同：普通文档树没有「层级到此为止」的标记，收集箱有。

规则：

1. 输出路径时，标题按原文照写，`/` 保持原样，不转义、不替换。`siyuan_list` 同时给出 oId，AI 两条信息都能看到。
2. 解析入参路径时，先按第一个 `/` 拆出虚拟笔记本名，剩下整段全部作为条目名，不再二次切分。
3. 条目名匹配顺序：先与 oId 精确比对；再与条目标题做全等比较（区分大小写敏感度按现有 `casefold` 规则）；出现多条同名时返回候选并提示改用 oId。
4. 因为第 2 步不做二次切分，标题里有没有 `/` 都不影响解析，不会处理到别的条目上。

对调用方：

- 用 `siyuan_list` 返回的路径直接读，标题含 `/` 也能命中。
- 重名时用 oId。
- 不需要考虑用哪种斜杠、要不要转义。

移出到普通笔记本时，写入内核的文档标题需要处理 `/`：内核 `createDocWithMd` 的 `documentBaseNameReplacer` 会把半角 `/` 直接删除，`createDocByParent` 允许保留但要求 Spec 6 及以上。为让两个版本分支结果一致，桥在写内核时把标题里的半角 `/` 换成全角 `／`。这只影响移出后的文档标题，不影响收集箱里的原始标题。

### 4.2 工具行为

| 工具 | 收集箱分支 |
|---|---|
| `siyuan_list(path=/收集箱)` | 调 `getShorthands` 分页，按 `limit/offset` 返回。每行给标题原文、oId、收藏时间、原文链接，均不截断；权限列固定 `read_only`。不输出 `shorthandMd` 正文 |
| `siyuan_list()` | 笔记本列表末尾追加 `收集箱 | - | read_only`，仅当非空 |
| `siyuan_read(path=/收集箱/<标题或oId>)` | 返回 `shorthandMd` 原文，前置一行来源提示（收藏时间、原文链接）。标题含 `/` 时路径里原样保留，桥只按第一个 `/` 拆到虚拟笔记本名，剩余整段当条目名。忽略 `include_block_ids`，返回普通阅读格式 |
| `siyuan_find` | 见 4.3 |
| `siyuan_edit` | 命中收集箱路径即报错（D11 文案） |
| `siyuan_doc_manage(action="move")` | 见 4.4 |

### 4.3 搜索纳入收集箱

`siyuan_find` 的 `query` 与 `regex` 两种模式，在原有搜索结果之外追加「收集箱」分组：

- 只匹配 `shorthandTitle`，不检索 `shorthandDesc` 与 `shorthandMd`。桥内不做云端正文检索，控制复杂度。
- 只拉到够用为止：逐页调 `getShorthands`，凑够 `limit` 条命中即停，不无条件翻完全部分页。
- 结果按现有格式渲染，标注属于收集箱，给出标题与 oId，供后续 `siyuan_read` / `siyuan_doc_manage` 使用。
- `mode=sql` 不纳入：SQL 走内核且收集箱不在块树，无法命中，保持现状。
- 若收集箱为空或接口不可用，静默跳过，不影响原有搜索结果。

### 4.4 移动流程

`siyuan_doc_manage(action="move", document_path="/收集箱/<标题或oId>", target_parent="/笔记本/父文档", confirmed=true)`：

1. 解析条目：先按标题精确匹配；多条同名时要求改用 oId，返回候选列表。标题匹配不到再试 oId。
2. 校验 `target_parent` 为可见 `read_write` 路径，复用现有目标解析。
3. 创建快照（沿用现有 `siyuan_doc_manage` 写入前快照）。
4. 按版本分支建文档（见 4.5），文档标题取 `shorthandTitle`，其中半角 `/` 换成全角 `／`（见 4.1b）。
5. 建文档成功后调用 `removeShorthands([oId])`。
6. 刷新索引，等路径可见后返回新文档路径。
7. 删除失败不撤销已建文档：返回结果里明确写出「文档已建立、收集箱条目未删除」，并给出新文档路径与 oId，供人工处理。

### 4.5 版本分支

用 `client.version()` 判断：

| 思源版本 | 建文档方式 |
|---|---|
| ≥ 3.8.9 | `planDocCreate` → `createDocByParent`（原生当前路径） |
| < 3.8.9，≥ 3.0.0 | `createDocWithMd`（现有 `client.create_doc_with_md`，v3.0.0 起全版本可用） |

两分支建出的文档在标题、路径、正文上一致，差别只在冲突检测与失败恢复粒度。桥对外返回结构统一。

### 4.6 刷新

沿用现有 `siyuan_doc_manage` 的等待路径 + 安全刷新机制，不为收集箱新加机制。收集箱删除是云端操作，不影响本地索引；新建文档需要刷新后才能被 list/read 命中，与现有 move/copy 行为一致。

## 6. 边界与风险

- 收集箱条目只存在云端，本地没有副本、没有文档 ID、不在块树与全文索引内。所有读取必须实时调云端接口，无法复用现有基于本地索引的读取与搜索路径。

- 收集箱条目没有 notebook 归属，现有按笔记本路径匹配的 Privacy Rules 命中不了。方案默认收集箱不受笔记本级隐私规则约束；若需要按标题或来源过滤，另行设计。
- `removeShorthands` 删除的是云端数据，工作空间快照无法恢复。建文档成功而删除失败时保留新文档并如实上报，不做自动回滚。
- `getShorthands` 每页都返回全量 `shorthandMd`（实测单条 2046–4525 字符）。列表与搜索必须裁剪输出，只有 `siyuan_read` 才回正文。
- 收集箱依赖云端连通；接口异常时 `siyuan_list` 不列出收集箱，`siyuan_find` 静默跳过，不阻塞本地能力。
