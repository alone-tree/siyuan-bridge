# 收集箱支持方案（2026-11-17）

> 草案，未实现。核对基准：思源v3.8.10（本机内核3.8.10）、仓库master、思源各版本tag源码。
> 定案实现后，工具契约并入`ARCHITECTURE.md`对应章节，本文删除。

## 1. 结论摘要

把收集箱做成一个虚拟笔记本，全部能力复用现有9个MCP工具，不新增工具：

- `siyuan_start`的笔记本概览表加一行`收集箱`，显示条目数。
- `siyuan_list`能看到`/收集箱`及其条目，`siyuan_list()`笔记本列表也列出它，权限列恒为`read_only`。
- `siyuan_read`能读条目，只走普通阅读，不提供引用阅读。
- `siyuan_find`能按条目标题纳入搜索。
- `siyuan_edit`、`siyuan_create`对收集箱路径直接拒绝。
- `siyuan_doc_manage(action="move")`把条目移入普通笔记本，移动即从收集箱删除。
- `siyuan_doc_manage(action="delete")`删除云端条目。

## 2. 已核实事实

### 2.1 收集箱在云端，本地无副本

| 核查项 | 结果 | 证据 |
|---|---|---|
| 数据来源 | 思源云端HTTP接口 | `kernel/model/cloud_service.go`的`GetCloudShorthands`请求`util.GetCloudServer() + "/apis/siyuan/inbox/getCloudShorthands?p=N"`，带`userToken` cookie |
| 本地文件 | 无 | `D:\\SiYuan\\data`下无inbox/shorthand目录；在`data/storage`与`data/.siyuan`搜索新条目oId`1794880590020`命中0 |
| 条目是否在块树 | 否 | `SELECT ... FROM blocks WHERE id='20261117084942-muvlgot'`为空；`getHPathByID`返回`tree not found` |
| 条目是否进FTS5 | 否 | 搜「私域肖厂长」命中的是用户自己剪藏的普通文档`20261104153808-iikoa4g`，不是收集箱条目 |

结论：云端剪藏条目只存在于云端，移动前本地没有副本。

### 2.1b 闪记是另一个功能，不是收集箱的本地实现

思源官方用户指南（`app/guide`术语表）原文：收集箱（Inbox）是临时存放待处理信息的容器，「在思源中，收集箱是云端快速记录功能，通过微信发送或API调用将文本暂存到云端，之后可在收集箱面板中将其移动到文档中进行整理。该功能需要订阅会员。」这是云端那套。

用户澄清：闪记和收集箱是两个东西。收集箱是云端功能，只有移动到普通笔记本后才进入本地文档体系；闪记是本地目录机制，独立于收集箱。下面记录闪记的事实，仅作区分参考，不纳入本方案：

| 证据 | 内容 |
|---|---|
| `kernel/util/working.go:250` | `ShortcutsPath // 用户家目录下的快捷方式目录路径 home/.config/siyuan/shortcuts/` |
| `kernel/model/shortcuts.go:29` | `shorthandsDir := filepath.Join(util.ShortcutsPath, "shorthands")` |
| `kernel/model/shortcuts.go:82` | 读`Conf.FileTree.Load().ShorthandSavePath`（配置注释为「闪念速记存储路径」） |
| 自动消费 | `AutoConsumeShorthandsJob`定时调`MoveLocalShorthands`，把本地shorthands目录内容转成文档 |
| 路由 | `/api/filetree/moveLocalShorthands`；v3.0.0无，v3.5.0 / v3.8.0 / v3.8.10 / master有 |

本机实测（2026-11-17）：`C:\\Users\\Zinger\\.config\\siyuan\\shortcuts`不存在，全盘无`shortcuts`目录；`conf.fileTree.shorthandSavePath`与`shorthandSaveBox`均为空串；前端构建包中`moveLocalShorthands`引用0次。本机只有云端那2条。

含义：两者的列表与移动接口完全不同，不能合并处理。本方案只处理收集箱（云端），闪记不在范围内。

### 2.2 账号状态

已登录。登录信息存放在`conf.userData`（加密串），不是`conf.user`；内核`Conf.GetUser()`解密后使用。运行时可证：`getShorthands`正常返回数据，未登录时内核会直接返回Language(31)错误。

### 2.3 实测可读

`POST /api/inbox/getShorthands {page:1}`返回2条：

| oId | 标题 | 收藏时间 | shorthandMd长度 | 原文链接 |
|---|---|---|---|---:|---|
| `1794880590020` | "没有人会逼一棵树说话" | 2026-11-17 09:56 | 2046 | mp.weixin.qq.com |
| `1792243354103` | 朋友圈反着发，越发，钱越追着你跑 | 2026-10-17 21:22 | 4525 | mp.weixin.qq.com |

条目字段（`kernel/apicontract/inbox.go`）：`oId`、`shorthandTitle`、`shorthandMd`、`shorthandContent`、`shorthandDesc`、`shorthandFrom`、`shorthandURL`、`hCreated`。

关键点：`shorthandMd`是原始Markdown（开头`---`+元数据列表+`## 标题`+正文+外链图），可直接写入文档；`shorthandContent`是lute渲染后的HTML预览，不用于写入。

分页结构：`pagination{paginationPageCount, paginationRecordCount, paginationPageNums}`；超出页码返回空数组，`paginationRecordCount`仍为真实总数。云端页大小由服务端决定，源码内无常量，桥不假设固定值。

无正文的条目：官方内核在返回列表时会把`shorthandDesc`里的音频、视频、文件链接替换成「语音」「视频」「文件」占位（`kernel/model/cloud_service.go:685-687`），说明语音类条目的正文形态与文章不同。桥不做类型分支，`shorthandMd`是什么就发什么，与思源原生移动一致。

### 2.4 原生接口与版本覆盖

| 接口 | 作用 | 版本覆盖 |
|---|---|---|
| `/api/inbox/getShorthands` | 分页列表 | v3.0.0起全部版本到master |
| `/api/inbox/getShorthand` | 单条全量 | 同上 |
| `/api/inbox/removeShorthands` | 删除云端速记 | 同上 |
| `/api/filetree/createDocByParent` | 身份式建文档 | v3.8.9起 |
| `/api/filetree/createDocWithMd` | 路径式建文档 | v3.0.0起全部版本 |

版本边界实测（`kernel/api/router.go`逐版本对比）：v3.0.0 / v3.8.0 / v3.8.8只有`createDocWithMd`；v3.8.9 / v3.8.10 / master多出`planDocCreate`与`createDocByParent`。`kernel/model/document_addressing.go`同样v3.8.5-v3.8.8为404，v3.8.9起存在。

本方案只用`createDocByParent`与`createDocWithMd`，不用`planDocCreate`。原因见2.5。

### 2.5 原生移动的真实链路

v3.8.10前端`Inbox.move()`：`getShorthand` → 本地组装请求 → `createDocByParent` → `removeShorthands`。

`planDocCreate`不在必经链路上：`app/src/util/configuredDocument.ts:99-113`只在调用方没传`plan`时才请求它，收集箱面板自己调`documentCreateRequest()`组装`{notebook, parentID, id, title:{format:"plain",text}, markdown}`后直接传给`createDocByParent`（`app/src/layout/dock/Inbox.ts:438-445`）。v3.8.9与v3.8.10同一套写法。

官方内核MCP`kernel/mcp/tools/inbox.go`的`convert`：能拿到结构化目标时用`model.CreateDocByParent`，否则用`model.CreateDocByMdSync`；只在成功条目上调用`RemoveCloudShorthands`。该双分支同样自v3.8.9起才出现，v3.8.8只有`CreateDocByMdSync`。

v3.8.0与v3.8.8前端`Inbox.move()`用路径式建文档后`remove(ids)`，切换点在v3.8.9。

`createDocByParent`的请求必填字段（`kernel/apicontract/document_addressing.go:19-36`）：`notebook`、`parentID`、`id`、`title`、`markdown`。`parentID`为`null`表示笔记本根。

### 2.6 标题斜杠与Spec

- `createDocByParent`保留标题里的半角`/`。内核`UpgradeSpec`会自动把含`/`的新文档升到Spec 6（`kernel/treenode/tree.go:216-222` + `kernel/documentaddressing/title.go:24`），调用方不需要声明，也不需要传`expectedParentRevision`。
- `createDocWithMd`的入参是hPath：`path.Base(hPath)`会先把`/A/B`切成`B`落在`/A`下面（`kernel/api/filetree.go:764-769`），`documentBaseNameReplacer`只兜底删除残留的半角`/`。也就是说路径式分支天然按斜杠分层。
- 两分支要产出一致结果，桥在写内核前把标题里的半角`/`换成全角`／`。这只影响移出后的文档标题，不影响收集箱里的原始标题。

### 2.7 原生面板的动作

收集箱面板右键菜单只有三项（用户 2026-11-17 截图）：刷新、移动、删除。移动与删除都支持多选，删除有二次确认弹窗（`app/src/layout/dock/Inbox.ts:281-319`）。本方案只做移动与删除，都是单条，不支持批量。

## 4. 实现设计

### 4.1 虚拟笔记本定位

虚拟名由桥在每次调用时按`knowledge_base/notebooks.json`缓存与真实笔记本名比对算出：

| 情况 | zh-CN | en |
|---|---|---|
| 无同名真实笔记本 | `收集箱` | `Inbox` |
| 已有真实笔记本叫`收集箱` | `收集箱(系统)` | `Inbox(System)` |
| 真实笔记本同时占用前两者 | `收集箱(系统)(2)` | `Inbox(System)(2)` |
| 依次递增 | `收集箱(系统)(n)` | `Inbox(System)(n)` |

比对用缓存，不额外请求内核。缓存过期可能算错一次，下次refresh后自愈。

展示条件（任一成立就不展示该虚拟笔记本）：

- 未登录或token失效（内核返回`code != 0`）
- 无订阅或权限不足（`code != 0`）
- 网络不可达或请求异常
- 收集箱确实为空（`code == 0`且`paginationRecordCount == 0`）

以上原因都只在桥内部判断，不把云端错误抛给调用方（`siyuan_read`、`move`、`delete`这类显式指向收集箱的调用除外，要如实报错）。

索引：收集箱不写入`knowledge_base/notebooks.json`，不写入`docs.jsonl`，不参与索引。

路径解析顺序：先按真实笔记本与文档匹配；没有真实匹配且路径落在当前算出的虚拟名下时，才走收集箱分支。虚拟名本身已避开重名，因此不会与真实笔记本冲突。

### 4.1b 标题含`/`的处理

关键前提：虚拟笔记本是单层的。`/收集箱/<条目名>`只有两级，第二级之后不再有层级，所以标题里的`/`不会被误当成下一级目录。这与其他工具的路径解析不同：普通文档树没有「层级到此为止」的标记，收集箱有。

规则：

1. 输出路径时，标题按原文照写，`/`保持原样，不转义、不替换。`siyuan_list`同时给出oId，AI两条信息都能看到。
2. 解析入参路径时，先按第一个`/`拆出虚拟笔记本名，剩下整段全部作为条目名，不再二次切分。
3. 条目名匹配顺序：先与oId精确比对；再与条目标题做全等比较（大小写不敏感）；出现多条同名时返回候选并要求改用oId。
4. 因为第2步不做二次切分，标题里有没有`/`都不影响解析，不会处理到别的条目上。

对调用方：

- 用`siyuan_list`返回的路径直接读，标题含`/`也能命中。
- 重名时用oId。
- 不需要考虑用哪种斜杠、要不要转义。

### 4.2 工具行为

| 工具 | 收集箱分支 |
|---|---|
| `siyuan_start` | 笔记本概览表追加一行`收集箱`：ID列`-`，文档数列为条目数，字数/块数列`-`，最近更新列取最新条目的收藏时间。收集箱为空或接口不可用时该行不出现 |
| `siyuan_list()` | 笔记本列表末尾追加`收集箱 \| - \| read_only`，仅当非空 |
| `siyuan_list(path=/收集箱)` | 调`getShorthands`分页，按`limit/offset`返回。列头`document \| document_id \| 权限 \| 收藏时间 \| 来源`，每行给标题原文路径、oId、`read_only`、收藏时间、原文链接，均不截断。不输出`shorthandMd`正文 |
| `siyuan_read(path=/收集箱/<标题或oId>)` | 返回`shorthandMd`原文，正文前一行来源提示（收藏时间、原文链接）。标题含`/`时路径里原样保留，桥只按第一个`/`拆到虚拟笔记本名。忽略`include_block_ids`、`block_start`、`block_limit`、`token_budget`、`include_images`，不做附件提取 |
| `siyuan_find` | 见4.3 |
| `siyuan_edit` | 命中收集箱路径即报错（D11文案） |
| `siyuan_create` | 命中收集箱路径即报错，提示收集箱只能移出或删除 |
| `siyuan_doc_manage(action="move")` | 见4.4 |
| `siyuan_doc_manage(action="delete")` | 见4.5 |
| `siyuan_doc_manage`其他action | 命中收集箱路径即报错，提示只支持move与delete |

`siyuan_read`也接受`document_id=<oId>`：oId是纯数字，与思源文档ID格式`YYYYMMDDHHMMSS-xxxxxxx`可区分。

### 4.3 搜索纳入收集箱

`siyuan_find`的`query`与`regex`两种模式，在原有搜索结果之外追加「收集箱」分组：

- 只匹配`shorthandTitle`，不检索`shorthandDesc`与`shorthandMd`。桥内不做云端正文检索。
- `query`模式按空白切词，全部命中标题即算匹配（与思源query模式的空格AND语义一致）。
- `regex`模式用Python正则对标题做`search`，表达式无效时跳过收集箱分组。
- 只拉到够用为止：逐页调`getShorthands`，凑够`limit`条命中即停，不无条件翻完全部分页。
- 结果追加在普通结果之后，单独一个二级标题，给出标题、oId、收藏时间，供后续`siyuan_read`与`siyuan_doc_manage`使用。
- 传了`notebooks`参数限定笔记本时不含收集箱。
- `mode=sql`不纳入：SQL走内核且收集箱不在块树，无法命中，保持现状。
- 若收集箱为空或接口不可用，静默跳过，不影响原有搜索结果。
- 结果末尾提示「收集箱只按标题匹配」。

### 4.4 移动流程

`siyuan_doc_manage(action="move", document_path="/收集箱/<标题或oId>", target_parent="/笔记本/父文档", confirmed=true)`：

1. 解析条目：先按oId精确匹配，再按标题全等匹配；同名多条时返回候选并要求改用oId。
2. 校验`target_parent`为可见`read_write`路径，复用现有目标解析。
3. 校验`confirmed=true`。
4. 创建快照。
5. 按版本分支建文档（见4.6），文档标题取`shorthandTitle`，其中半角`/`换成全角`／`（见4.1b）。正文取`shorthandMd`。
6. 建文档成功后调用`removeShorthands([oId])`。
7. 刷新索引，等路径可见后返回新文档路径与文档ID。
8. 删除失败不撤销已建文档：返回结果里明确写出「文档已建立、收集箱条目未删除」，并给出新文档路径、文档ID与oId，供人工处理。

同名不检查：目标位置已有同名文档时照常创建，两篇文档都由ID区分（D20）。

### 4.5 删除流程

`siyuan_doc_manage(action="delete", document_path="/收集箱/<标题或oId>", confirmed=true)`：

1. 解析条目，规则同4.4第1步。
2. 校验`confirmed=true`。
3. 直接调用`removeShorthands([oId])`，不创建快照（快照只覆盖本地工作空间，恢复不了云端条目）。
4. 返回删除结果，并提示该操作不可恢复。

### 4.6 版本分支

用`client.version()`判断：

| 思源版本 | 建文档方式 |
|---|---|
| ≥ 3.8.9 | `createDocByParent`（`{notebook, parentID, id, title:{format:"plain",text}, markdown}`，`parentID`为`null`表示笔记本根） |
| 3.3.0 - 3.8.8 | `createDocWithMd`（现有`client.create_doc_with_md`，v3.0.0起全版本可用） |

两分支建出的文档在标题、位置、正文上一致，差别只在冲突检测与失败恢复粒度。桥对外返回结构统一。

### 4.7 刷新

沿用现有`siyuan_doc_manage`的等待路径+安全刷新机制，不为收集箱新加机制。收集箱删除是云端操作，不影响本地索引；新建文档需要刷新后才能被list/read命中，与现有move/copy行为一致。

## 6. 边界与风险

- 收集箱条目只存在云端，本地没有副本、没有文档ID、不在块树与全文索引内。所有读取必须实时调云端接口，无法复用现有基于本地索引的读取与搜索路径。
- 收集箱条目没有notebook归属，现有按笔记本路径匹配的Privacy Rules命中不了。方案默认收集箱不受笔记本级隐私规则约束。
- `removeShorthands`删除的是云端数据，工作空间快照无法恢复。建文档成功而删除失败时保留新文档并如实上报，不做自动回滚。
- `getShorthands`每页都返回全量`shorthandMd`（实测单条2046-4525字符），内核还会对每条做lute解析与ProtylePreview渲染HTML（实测HTML体积是Markdown的2.2-2.8倍）。列表与搜索必须裁剪输出，只有`siyuan_read`才回正文。
- 收集箱依赖云端连通；接口异常时`siyuan_list`不列出收集箱，`siyuan_find`静默跳过，不阻塞本地能力。
- 同名文档允许并存后，同名路径在`siyuan_read`等工具里会报歧义，需要用`document_id`。这与思源自身行为一致。

## 7. 验证要求

按`docs/DEVELOPMENT_GUIDE.md`的分层验证：

1. 单元测试覆盖上述分支。
2. 能力库`siyuan-bridge-dev`真实调用：列收集箱、读条目、读时带`include_block_ids`被忽略、edit被拒、create被拒、搜索命中、移动到普通笔记本并确认快照与删除、删除条目、移动后新文档可读、标题重名歧义报错、空收集箱不展示。
3. 旧版分支需在v3.3.0-v3.8.8的实例上实测一次`createDocWithMd`回退；当前无该版本实例时标记未验证。
