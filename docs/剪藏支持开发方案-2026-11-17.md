# 剪藏支持开发方案

状态：已定稿，等待实现。2026-11-17。

本文是 `siyuan_create` 支持从 URL 建文档的完整开发指导。它回答两件事：要做什么，为什么这样做。实现完成后按文档规范把「当前架构」部分并入 `ARCHITECTURE.md`，本文删除。

## 1 背景与目标

### 1.1 要解决什么

用户在浏览网页时看到值得保存的内容，现在的路径是先复制正文、再让 AI 写进思源，或者用浏览器扩展手动剪藏。前者要用户自己判断正文边界，后者要用户离开 AI 会话去点扩展。

目标是让 AI 一句话完成：给一个 URL，存成思源文档，正文干净、图片下载到本地、结构符合思源习惯。

### 1.2 明确的非目标

- 不做无头浏览器。不引入 Chromium、Playwright、Node。
- 不做通用爬虫。不遍历链接、不做站点发现、不做增量抓取、不维护 URL 队列。
- 不为站点写适配规则。唯一的例外是微信，见 3.3。
- 不覆盖需要登录态的页面。用户浏览器里的 Cookie 不借用。

### 1.3 为什么不做无头浏览器

三层都查过了，思源本体没有可直接借用的渲染能力：

内核 723 条路由里 `puppeteer`、`chromedp`、`rod`、`playwright`、`selenium` 全零命中。与抓取相关的只有 `/api/network/forwardProxy`（裸 HTTP 转发）和 `/api/extension/copy`（接收已抓好的 HTML 字符串，参数是 `dom` 不是 URL）。

内核自带 MCP 服务的 `web_fetch` 是裸 HTTP。实现 `kernel/util/webfetch.go` 走 `ssrfSafeClient` 直接 GET，5 MiB 上限，50000 字符截断，`SanitizeHTML` 清完用 lute 的 `HTML2Markdown` 整页转 Markdown，不做正文抽取。本机实测：

```text
[阮一峰]  len=22173 img=42  head='阮一峰的网络日志  » [首页](...) » [档案](...)'
[少数派]  len=16393 img=43  head='[  共创  ](/create) \n\n[  PRIME  ](/prime)'
[MDN]     len=13098 img=0   head='- [跳转到主要内容](#content)\n- [跳转到搜索](#mdn-search)'
[arXiv]   web_fetch error: fetch failed
[GitHub]  web_fetch error: fetch failed
```

开头全是导航。arXiv 和 GitHub 直接失败，因为内核走直连、没有代理配置。同一篇微信文章经它抓取，返回 72 字符的验证页「环境异常，完成验证后即可继续访问」。

Electron 桌面端有真正的离屏浏览器，在 `app/electron/remote/webPageFetch.ts`：`BrowserWindow` 加 `javascript: true`、`offscreen: true`、`sandbox: true`，每次抓取独立 session 不带用户 Cookie，自定义 protocol handler 固定公网 IP 防 SSRF，禁下载禁 WebSocket 禁 WebRTC，最多 3 并发。

但它注册为 agent 能力 `native/frontend/web_page_fetch`，条件写死在 `app/src/layout/dock/agent/frontendCapabilities.ts`：

```ts
/// #if !BROWSER && !MOBILE
if (!mobileFrontend && !isBrowser()) {
    registerCapability({ id: "native/frontend/web_page_fetch", ... })
}
```

走 IPC 通道 `siyuan-web-page-fetch`，只给应用内 Agent，不投影到外部 MCP。实测内核 `tools/list` 返回 31 个工具，没有它。

复用它还有额外代价：Chrome 和 Edge 已移除侧载扩展所需的命令行标志（Playwright 官方文档明说），要程序驱动就得自带 428 MB 的 Chromium，且那个浏览器里同样没有用户的知乎、Medium 登录态。收益接近零。

### 1.4 为什么不复用浏览器扩展

官方扩展 `permissions` 只有 `contextMenus`、`storage`、`commands`。`externally_connectable`、`nativeMessaging`、`debugger` 全部缺失，没有任何对外通道。

`content.js` 读的是 `document.title`、`window.location.href`、`document.body`，只能剪当前已打开页面，从来不具备「给一个 URL 去剪」的能力。`background.js` 的标签页操作只有 `query`、`sendMessage`、`create`，没有 `update` 或导航。

### 1.5 它借鉴了什么

Electron 那段代码里的正文抽取规则值得照搬，形态而不代码：

```js
const selectors = ["main", "article", "[role=main]", ".main-content", "#main-content",
  ".article-body", ".post-content", ".entry-content", ".content", "body"];
```

取 innerText 最长且不少于 100 字符的那个，再移除 `script, style, noscript, template, iframe, object, embed, nav, [hidden], [aria-hidden=true]`。

这证明思源自己抓整页时也是「语义标签优先 + 固定门槛」，不为任何站点写特例。我们采用同一思路，代码用 Python 重写。

## 2 核心设计决策

| 决策 | 内容 | 理由 |
|---|---|---|
| 工具面 | `siyuan_create` 增加 `source_url` 参数 | 复用现有路径解析、权限检查、快照、写后刷新；不新增第 10 个工具 |
| HTML 转 Markdown | 交给内核 `/api/extension/copy` | 内核的 lute 是思源格式的唯一真源，产出与手写文档一致；自研转换实测明显更差 |
| 正文定位 | 语义容器 → 文本密度 → `body` 兜底 | 通用规则，覆盖 18/31 站点，无需站点适配 |
| 图片 | 默认本地化，不提供开关 | 用户明确要求默认本地化；外链图会随时间失效 |
| 依赖 | 优先标准库，必要时最小外部依赖 | 见 4 |
| 同名重复剪藏 | 沿用现有 `if_exists` 三值，默认 `reject` | 用户明确要求与现有行为保持一致，让用户自己决定是否刷新 |
| 字符编码 | 网页按网页自己的声明顺序判定 | 用户明确要求按网页的合理顺序，不复用本地文件的兜底规则 |
| 内网地址 | 与思源内核保持一致，禁止访问内网与回环地址 | 用户明确要求；思源内核的 `web_fetch` 已有同类防护，本功能对齐它 |

关键实测对比，说明为什么转换必须交给内核。同一篇微信文章：

| 转换方式 | 产出 | 图片 |
|---|---|---|
| 内核 `/api/extension/copy` | 11022 字符 | 26 到 29 张 |
| trafilatura 2.3.1 | 5553 字符，前插 9 行 YAML 头 | 0 张 |
| readability-lxml 0.9 | 4599 字符 | 0 张 |
| 内核 `web_fetch`（整页无抽取） | 72 字符验证页 | 0 张 |

## 3 实现设计

### 3.1 整体链路

```text
siyuan_create(source_url=...)
  → 抓 HTML（urllib，浏览器 UA，走系统代理，30 秒超时，上限 5 MiB）
  → 标准库 html.parser 建轻量树
  → 定位主容器
  → 清洗（删噪音标签、只留 src/href/alt、提升懒加载图、section 改 div）
  → POST /api/extension/copy（clipType=article, assets=false）拿 Markdown
  → 提取标题（og:title → <title> → URL 末段）
  → 走现有 create 写入（路径解析、权限、快照、if_exists）
  → /api/format/netImg2LocalAssets 本地化图片
  → 索引刷新与返回
```

抓取和转换全部在快照之前。任何一步失败都不写思源、不创建快照。

### 3.2 抓取层

新增函数，建议放在新建的 `source_code/clip.py`，避免继续撑大 `mcp_server.py`。

- 用 `urllib.request`，不新增依赖。
- 请求头：浏览器 UA（Chrome 131 桌面版）、`Accept-Language: zh-CN,zh;q=0.9,en;q=0.8`、`Accept: text/html,application/xhtml+xml,...`。
- 走系统代理：`urllib` 默认读环境变量与注册表。实测本机 `HTTP_PROXY=http://127.0.0.1:17891` 可用；清空环境变量后海外站点 TLS 握手超时。不要主动构造 `ProxyHandler`，保持默认行为，让部署环境决定。
- 超时 30 秒。读取上限 5 MiB，超限即中止并报错。
- 编码判定顺序：`Content-Type` 的 `charset` → HTML 前 4KB 的 `<meta charset>` → UTF-8。这是通用类型适配，不是站点适配。GBK 站点（新浪、新华网）靠它正确解码。这条顺序是用户已确认的要求，与 `markdown_file` 的本地文件顺序不同，见 7.2。
- 抓取前先解析主机名并拒绝内网、回环与 IPv6 过渡地址，对齐内核 `web_fetch` 的行为，见 7.3。
- `Content-Type` 分流：`text/html`、`application/xhtml+xml` 走正文定位；`text/plain`、`text/markdown` 直接当正文；其他类型（PDF、图片、二进制）明确报错不处理。
- HTTP 状态非 2xx 直接报错，带上状态码。

### 3.3 正文定位

用标准库 `html.parser` 建一棵轻量 DOM 树。每个节点只需 `tag`、`attrs`、`children`、`text`、`parent` 五个字段。

按顺序尝试，命中即停：

1. 语义容器，按选择器优先级：`#js_content`（微信）、`article`、`main`、`[role=main]`、`#main-content`、`.article-content`、`.post-content`、`.entry-content`、`.content`。命中条件：节点可见文本长度 ≥ 200 且 ≥ 全页文本的 15%。
2. 文本密度扫描：遍历所有 `article`、`main`、`div`、`section`，计算 `文本长度 - 2 × 链接文本长度`，按 `/(1 + 0.08 × DOM 深度)` 衰减，取最高分。
3. 都失败就退回 `body`。

站点专属规则只有第 1 步里的 `#js_content`。它是微信图文文章的正文容器 id，语义明确，且微信是用户明确要求支持的渠道。在代码里用注释标注这是唯一例外，新增任何站点 id 都需要用户授权。

实测这套规则在 8 个站点的表现（与 bs4 三件套对比，结果接近）：

| 站点 | 抽中容器 | 正文文本 | 转出 Markdown | 图片 | 耗时 |
|---|---|---|---|---|---|
| 微信 | `#js_content` | 5540 | 11022 | 26 | 76 ms |
| 阮一峰 | `div`（密度） | 5417 | 14462 | 40 | 24 ms |
| 少数派 | `article` | 5291 | 14100 | 37 | 39 ms |
| 掘金 | `article` | 34205 | 54376 | 5 | 172 ms |
| 新浪 | `.article-content` | 1054 | 10357 | 18 | 88 ms |
| Wikipedia | `main` | 20747 | 52011 | 3 | 65 ms |
| GitHub | `article` | 1881 | 4488 | 7 | 54 ms |
| MDN | `main` | 1375 | 6151 | 0 | 35 ms |
| arXiv | `main` | 4450 | 11601 | 2 | 28 ms |
| CSDN | `article` | 3784 | 4930 | 3 | 47 ms |

### 3.4 清洗

这一步决定产出质量，不能省。

- 删除标签：`script`、`style`、`noscript`、`svg`、`iframe`、`form`、`button`、`select`、`textarea`、`canvas`、`template`。
- 所有元素只保留 `src`、`href`、`alt` 三个属性，其余全部删除。这一条不可省：微信每个 `<span>` 都带完整内联样式，不删的话内核会把样式转成 IAL 属性语法，实测产出 39270 字符垃圾；删完是 11022 字符干净正文。
- `<img>` 的 `data-src`、`data-original`、`data-lazy-src` 提升为 `src`。微信的图全在 `data-src` 上（实测页面上 `data-src` 出现 72 次而 `<img>` 只有 35 个），不提升则 26 张图全丢。
- `section` 改名为 `div`，避免内核生成超级块。
- 属性值里的相对 URL 按页面 `base` 补全为绝对 URL；非 http/https 的 scheme 直接去掉该属性。

### 3.5 转换成 Markdown

调用内核 `/api/extension/copy`，multipart 表单：

| 字段 | 值 |
|---|---|
| `dom` | 清洗后的 HTML 片段 |
| `clipType` | `article` |
| `href` | 原始 URL |
| `assets` | `false`（图片由后续本地化处理，不走这条上传通道） |

返回 `{"code":0,"data":{"md":"...","withMath":false}}`，取 `data.md`。

该端点自 v3.0.0 起所有版本存在，不在官方 API 文档里（`docs/API.zh-CN.md` 检索 `api/extension` 命中 0 处），属内核内部接口。用它是权衡结果：官方文档写明「只有在本文档中设有独立接口说明的接口属于公开 API」，但内核自己的 MCP 和浏览器扩展都在用这个端点，且它是唯一能保证产出格式与思源一致的方式。

### 3.6 标题提取

优先级：`og:title` → `<title>` → URL 末段（去掉查询串与扩展名）。

传了 `source_url` 时，`siyuan_create` 的 `title` 参数变为可选。用户显式传 `title` 时以用户为准。

### 3.7 工具面改动

`tool_specs()` 中 `siyuan_create` 的改动：

- `required` 从 `["title", "confirmed"]` 改为 `["confirmed"]`。
- `markdown` 描述从「与 markdown_file 互斥」改为「与 markdown_file、source_url 三选一」。
- `markdown_file` 描述同步改为三选一。
- 新增 `source_url` 属性：

```text
Fetch a web page and use its body as the document content. Mutually exclusive with markdown and markdown_file. When set, title is optional and defaults to the page title. Images in the page are downloaded into the SiYuan asset library by default. Pages that need login or JavaScript rendering cannot be fetched and the call fails before any write.
```

- 总描述补一句，说明可以给 URL。

改描述前必须完整读 `DEVELOPMENT_GUIDE.md` 的「编写 MCP 工具描述」。

### 3.8 参数校验

在 `siyuan_create` 开头、快照之前：

- 三个正文来源必须且只能给一个。多给或都不给时报 `validation:markdown_conflict`，错误信息列出三者并说明只能给一个。
- 给了 `source_url` 时 `title` 允许为空，由抓取结果补；其他情况 `title` 仍必填。

### 3.9 抓取与转换的失败处理

全部在快照之前，直接抛错，不写思源：

| 情况 | 错误码 | 报错要点 |
|---|---|---|
| URL 不是 http/https | `validation:invalid_url` | 说明只接受 http 与 https |
| 主机名解析出的地址命中内网/回环段 | `validation:blocked_address` | 说明这是安全限制，不是网络问题；对齐内核 `web_fetch` 的行为，见 7.3 |
| 网络不可达、超时 | `api:clip_fetch_failed` | 带上底层原因；提示检查网络或代理 |
| HTTP 状态非 2xx | `api:clip_fetch_failed` | 带上状态码 |
| 响应超过 5 MiB | `api:clip_too_large` | 说明上限 |
| 页面无正文 | `api:clip_no_content` | 提示可能是 JS 渲染页面，建议用浏览器扩展手动剪藏 |
| 命中反爬验证页 | `api:clip_blocked` | 说明需要登录或验证，建议用浏览器扩展 |
| 内核转换失败 | `api:clip_convert_failed` | 带上内核返回的 msg |

反爬验证页的识别用特征词，命中即判失败：`环境异常`、`访问受限`、`Just a moment`、`Please enable JS`、`Security Verification`、`Sina Visitor System`、`zh-zse-ck`。这是通用特征，不是站点规则。

### 3.10 图片本地化

写入成功后，对文档 ID 调用 `/api/format/netImg2LocalAssets`，body `{"id": "<doc_id>"}`。

实测：微信文章 26 到 29 张外链图，调用后 `markdown LIKE '%mmbiz%'` 计数归零、`markdown LIKE '%assets/%'` 变成 26，文件真实落在 `data/assets/network-asset-*.png`，单张 224 KB 量级。

该接口返回 `{"code":0,"msg":"","data":null}`，没有逐项结果。失败不阻塞正文，按现有 create 的部分完成约定上报，保留文档 ID，不重建整篇文档。

### 3.11 写入流程的位置

在现有 `siyuan_create` 的第 11 步之后插入图片本地化：

1. 校验（含三选一）
2. 使用 `source_url` 时先抓取并转换，得到 markdown 与默认标题
3. 校验 title
4. 解析目标路径与 live 文档判断
5. 权限检查
6. 拒绝 Privacy Rules 文档
7. `if_exists` 决策
8. `overwrite` 反链检查
9. 创建快照
10. 去重首 H1
11. 创建或覆盖文档
12. `markdown_file` 的本地引用处理
13. 图片本地化（新增）
14. pushMsg
15. 路径同步等待
16. 索引刷新
17. 返回

### 3.12 返回值

在现有返回格式里增加：

- 使用 `source_url` 时，输出一行说明来源 URL 与抓取到的原始标题。
- 图片本地化结果：成功写「图片已本地化 N 张」；失败写实际状态并保留文档 ID。
- 抓取阶段的任何失败都不产生文档写入。

## 4 依赖

遵循「最小外部依赖」原则（见 `ARCHITECTURE.md` 的「第三方依赖」）：能用标准库就用标准库；标准库做不到或做不好时才引入少量包；组件自动下载、多镜像源、SHA-256 校验，用户零配置。

本功能首选不新增依赖，用标准库 `html.parser`。

三种方案实测对比：

| 方案 | 依赖体积 | 实测表现 |
|---|---|---|
| 标准库 html.parser | 0 | 10 站点抽取结果与 bs4 接近，耗时 24 到 172 ms |
| bs4 + soupsieve + typing_extensions | 204 KB | 结果接近，耗时 45 到 569 ms，需扩展现有 wheel 机制支持纯 Python 包 |
| trafilatura 全树 | 6.88 MiB（15 个包，3 个编译型） | 微信 0 张图，正文前插 9 行 YAML 头，MDN 截断到 618 字符 |

标准库版在微信上比 bs4 更快且图片更多。唯一取舍是 `html.parser` 对畸形 HTML 的容错比 lxml 差；兜底策略是解析异常或抽不到容器时退回整页 `body`，交给内核转换。如果实现中发现容错确实不够，再按最小依赖原则引入 bs4 三件套，同时扩展现有 wheel 机制支持多包与纯 Python 包。

## 5 能力边界

### 5.1 站点分布

31 个站点实测：

| 类别 | 数量 | 例子 |
|---|---|---|
| 直连可抓 | 18 | 微信图文、阮一峰、少数派、CSDN、虎嗅、新浪、GitHub、arXiv、MDN、Wikipedia、BBC、Guardian |
| JS 壳 | 3 | 今日头条（72914 字节可见文本 0）、B站专栏、豆瓣文章 |
| 反爬或登录墙 | 8 | 知乎 403、Medium 403、StackOverflow 403、Reuters 401、简书 403、微博 Visitor System |
| 传输阻断或付费墙 | 2 | 小红书 TCP 重置、NYT 计量墙 |

### 5.2 微信的三种页面

| 页面类型 | 判定特征 | 可抓 | 说明 |
|---|---|---|---|
| 普通图文文章 | `<div id="js_content">` 存在且内含正文 | 是 | 正文在静态 HTML 里，实测可见文本 5828 字符 |
| 图片消息页 | `class="share_content_page"`，`js_base_container` 为空壳 | 否 | 正文由 JS 渲染 |
| 纯图片消息页 | 同上，且正文本身就在图里 | 否 | 无正文可抽 |

图片消息页的实测数据（`https://mp.weixin.qq.com/s/6mwhyTxtWBa6GUmaRa9iQQ`，用户确认 17 张图）：

- 页面 2634619 字节，可见文本仅 136 字符，且全是「知道了／微信扫一扫／取消／允许」这类壳文案。
- `picture_page_info_list` 数组的顶层对象正好 17 个，与图数一致，每个带 `cdn_url`、`width`、`height`，全部 2160x2880。
- 正文容器 `<div class="share_content_page_bd" id="js_base_container"></div>` 是空壳。
- 对照实验 `https://mp.weixin.qq.com/s/2KmBNt2fD1j3sBpylT_Qaw`（12 图 + 正文）同结构，顶层对象正好 12 个，同样拿不到正文。

用户裁决：暂不支持。

### 5.3 编码与类型适配

允许按内容类型分支，不允许按站点分支：

- 字符编码：Content-Type 的 charset → 前 4KB 的 `<meta charset>` → UTF-8。
- 内容类型：`text/html` 走正文定位；`text/plain`、`text/markdown` 直接当正文；其他类型报错。
- 反爬特征词：见 3.9，通用特征不是站点规则。

## 7 用户已确认的三项要求

2026-11-17，就该方案提出的三个分歧，用户答复如下。这三条是实现时必须遵守的约束，不是可选做法。

### 7.1 同名重复剪藏：与现有行为保持一致

原话：「默认保持一致。让用户自己刷新」。

即沿用现有 `if_exists` 三值，默认 `reject`。同一个 URL 再次剪藏时，如果目标路径已有同名文档，默认拒绝，由用户在需要刷新时显式传 `if_exists=overwrite`。

不为剪藏引入「相同 URL 视为同一文档」的特殊判断，也不新增来源 URL 的记录机制。

### 7.2 字符编码：按网页自己的合理顺序

原话：「按网页和合理顺序来」。

即使用 3.2 的网页判定顺序：`Content-Type` 的 `charset` → HTML 前 4KB 的 `<meta charset>` → UTF-8。

这一条明确不同于 `markdown_file` 的本地文件顺序（UTF-8 → GBK → GB18030）。两者不统一，也不互相复用：本地文件没有 HTTP 头可依据，网页有。实现时两处各按各自规则写，不要为了「统一」把网页也套上 GB18030 兜底。

### 7.3 内网地址：与思源内核保持一致

原话：「这个功能的用途是把网络文章保存到思源，和思源内核保持一致」。

即本功能的地址校验对齐思源内核对 `web_fetch` 的处理，禁止访问内网与回环地址。

思源内核的做法（`kernel/util/httprequest.go`）：

- 抓取前先解析主机名，用 `checkHostSSRFContext` 检查解析出的所有 IP，任一命中私有地址段即拒绝，报错 `access to private/internal IP is prohibited`。
- 校验函数注释说明它覆盖 NAT64、6to4、Teredo 等 IPv6 过渡地址。
- `ssrfSafeClient` 在直连时把目标固定到已校验的公网 IP，走代理时先与代理建立隧道再连固定后的目标 IP，两种方式都不在校验后重新按域名解析，避免 DNS 重绑定 TOCTOU 绕过。
- 相关安全公告：GHSA-rg26-cg95-gq6p、GHSA-x8gv-g2g3-65fj。

实现时按同样思路：抓取前解析主机名，拒绝解析结果中的私有地址、回环地址、链路本地地址和 IPv6 过渡地址；报错文案说明这是安全限制而不是网络问题。具体地址段清单以内核 `kernel/util/net.go` 的 `isPrivateIP` 为准，实现时对照该函数，不要自行发明清单。

这条要求的直接后果是：本机部署的内部 Wiki、局域网服务不能用这个功能剪藏。这是有意的取舍，用户已确认。

## 8 未决与风险

- 内核 `/api/extension/copy` 不在官方 API 文档里。如果未来内核移除或改签名，剪藏会失效。缓解：单测覆盖该端点调用，失败时报错明确说明；`docs/思源API.md` 已标注它是内部接口。
- 大页面（如 263 万字节的微信页）解析内存占用未实测。实现时应在抓取阶段就按 5 MiB 截断，避免解析超大 HTML。
- 图片消息页如果后续要支持，唯一路径是引入无头浏览器，与当前设计前提冲突。
